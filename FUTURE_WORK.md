# Future work

This is a list of things this dataset makes possible that we have not done, plus
the things that would have to be built first. It is written for someone deciding
whether to pick the data up, so it says what the data actually contains and what
it does not support, not only what would be interesting.

Nothing here is a claim about results. Where we ran something, it is marked.

---

## What the data actually gives you

Numbers below are measured on the released `arc_agi1` config (400 makers, one per
task of the ARC-AGI-1 training split, ten episodes each).

| Property | Value |
|---|---|
| Episodes | 4,000 |
| Transitions | 58,155 |
| Distinct operations | 33 |
| Episode length | min 1, median 7, mean 14.5, p90 30, max 407 |
| Reward | 0 everywhere, 1 on the terminal `Submit` |
| Worked examples per episode | 3 (input/output pairs, the episode's own pair never among them) |
| State per step | grid, clip, selection mask, selected, object, object mask, background, all dims and positions |

Four properties matter more than the size.

**The action space is discrete and spatial at once.** An action is one of 33
operations *plus* a selection over the grid. The operation is a small
categorical; the selection is a variable region on a variable-size canvas. Most
offline RL benchmarks give you one or the other.

**The reward is sparse and terminal.** One bit, at the end, after a median of 7
and sometimes 407 actions. There is no shaped signal anywhere in the data.

**The operation distribution is extremely uneven.** `Color*` accounts for about
60% of all actions; `Rotate90` for 0.1%. A policy that never learns to rotate
loses almost nothing on token-level loss and fails the tasks that need it.

**The state is complete, not just the grid.** Every step records the full ARCLE
environment, so a model can be given, or asked to predict, the clipboard,
the selection, and the object buffer, not only the visible canvas.

And one property that is not about a single episode:

**The dataset is a sample, not a corpus.** Every task ships an executable
`grid_maker.py`. Rolling it out again gives fresh inputs from that task's RE-ARC
generator and a fresh solving trajectory. 4,000 is one draw. This is unusual
enough that several directions below exist only because of it.

## Directions

### 1. Offline RL with a sparse terminal reward and a long horizon

This is the direction the data was built for, and the one we have actually
worked on. The setting is hard in the specific ways offline RL is known to be
hard: the reward is one terminal bit, the horizon is long and heavy tailed, and
the behaviour policy is a single expert route per episode with no negatives.

Open, in rough order of how much we would want to see them:

- **Behaviour cloning as the honest floor.** No published number exists for
  "just clone the routes and replay". Whatever it is, everything else should be
  measured against it, and it should be reported per task, not pooled, because
  pooling hides that a handful of long tasks dominate the transition count.
- **Latent skill / option discovery.** Median 7 actions but a p90 of 30 means
  most episodes are short and a minority carry the horizon. Whether useful
  temporal abstractions fall out of 58k transitions, or whether they need the
  larger draws that the makers allow, is unresolved.
- **Value learning under one-bit terminal reward.** Standard offline value
  methods (CQL, IQL and relatives) have not been run here as far as we know.
  The failure mode to watch for is trivial: with all-positive data, a critic can
  score everything highly and still be useless.
- **Factorised action heads.** Predicting the operation and the selection jointly
  versus separately is an open design question and cheap to ablate.

### 2. Step-level verification and process supervision

ARC has an unusual property among reasoning benchmarks: **an intermediate state
is checkable**. In a maths chain of thought there is no way to test step 4 in
isolation. Here, step 4 is a grid, and a grid either is or is not what the
operation should have produced.

That makes this data a natural place to train and evaluate:

- **A process reward model.** Score partial trajectories rather than final
  answers. The data gives positives directly; negatives can be generated by
  perturbing an action and replaying, which costs nothing and is exactly
  labelled because ARCLE is deterministic.
- **Step-level critics for search.** A policy that proposes actions plus a critic
  that prunes states is a very different system from one that emits an answer
  grid, and it is testable here in a way it is not on most benchmarks.
- **Failure attribution.** When a rollout misses the target, the first step at
  which it diverges from a valid route is recoverable. Almost no reasoning
  dataset supports that.

We built none of this. The perturb-and-replay negative generator is the piece we
would write first; it is a small script on top of `pipeline/gen_rearc_trajectories_v2.py`.

### 3. Trajectory-conditioned in-context learning

The `demo` subset exists for this. In it, **the worked examples are not just
input/output pairs; each one also has its own recorded trajectory.** So a model
can be prompted with *how* the demonstrations were solved, not only with what
they turned into.

The obvious experiment has not been run: few-shot ARC where the shots are
routes rather than pairs, against the same model with pair-only shots. If
showing the route helps, that is an argument about what demonstrations should
contain that reaches well past ARC.

Note the subset's shape before using it. Each family fixes three demonstrations
and then makes each pair in turn the target, including the demonstration pairs
themselves, so a demonstration row does see its own pair among its examples.
That is deliberate: the subset is there to show that the example pairs are
solvable step by step too. It is a visualisation set. It is **not** a
leave-one-out few-shot benchmark and should not be used as one without
rebuilding the example sets.

### 4. Route quality, not route length

Every task here has at least one recorded route. Some have several: the
`handcraft` subset ships hand-written variants of the same task that reach the
same target by different means.

The question we care about and did not answer is what makes a route good. It is
**not** shortness. A route that collapses a task into one opaque `Paste` is
worse, for a learner, than a longer route that does the thing the task is about
in visible steps. But "worse" is currently an opinion, not a measurement.

Concretely testable:

- Train on short routes versus long routes for the same tasks and compare
  transfer to held-out tasks.
- Check whether models trained on one route family generalise to targets that
  need another.
- Measure whether the operation used correlates with the task's underlying
  concept, or only with the maker author's habits.

The last one is a real risk to the dataset and worth stating plainly: 400 of the
routes come from one generation pipeline, so stylistic regularities in them may
be learnable shortcuts that have nothing to do with ARC.

### 5. Scaling, because the makers are generators

Almost no ARC dataset can vary its own size. This one can, along two axes that
are usually confounded:

- **Episodes per task**, holding the 400 tasks fixed. Rolling out at 10, 50, 250
  episodes per task answers how much of the difficulty is coverage of the input
  distribution.
- **Tasks**, holding episodes per task fixed. Requires new makers, which is the
  expensive axis, but the pipeline for writing them is in this repository.

Separating those two is the experiment we would most like to see, and it is
mostly CPU time rather than research risk. `pipeline/gen_rearc_trajectories_v2.py`
regenerates trajectories from the makers in minutes without any model calls.

A caveat that has to be carried through any such study: inputs come from RE-ARC
generators, not from the original ARC pairs. The generators are broader than the
originals by design, so "more episodes" means more of the RE-ARC distribution,
which is not identical to the ARC distribution.

### 6. ARC-AGI-2

Fifty construction makers for real ARC-AGI-2 training tasks exist and pass
replay at 46/50, but they are not in this repository and not published; thirty
tasks are browsable in the viewer as a beta subset. Publishing them is a
separate piece of work, tracked outside this document.

Once they are out, the question is transfer: whether a policy trained on
ARC-AGI-1 routes does anything at all on ARC-AGI-2, given that AGI-2 was
constructed specifically to defeat systems that do well on AGI-1. Our
expectation is that it does not, and that saying so with a number is more useful
than not testing it.

### 7. The recipe outside ARC

The pipeline here does something more general than making an ARC dataset: it
gets a model to write an **executable solution** rather than an answer, and then
uses execution to check it. The check is not "did the model claim the right
output" but "does running this code, in this environment, reach the target".

That pattern needs three things: a deterministic environment, a way to sample
tasks, and a target that can be compared exactly. Anywhere those hold, the same
loop applies, and it produces trajectories rather than labels. Whether it is
worth the trouble outside puzzle domains is untested.

## What would have to be built

Ordered by how much they unlock relative to effort.

1. **Perturb-and-replay negative generator.** Unlocks direction 2 entirely.
   Small, deterministic, no model calls.
2. **A behaviour-cloning baseline with a per-task report.** Unlocks honest
   comparison for everything in direction 1.
3. **A rollout harness that scales episodes per task.** Mostly exists; needs a
   sweep driver and a place to put the output. Unlocks direction 5.
4. **Example-set rebuilding for the demo subset.** Needed only if someone wants
   a true leave-one-out few-shot benchmark out of it. Cheap: the trajectories
   stay, only the example lists are reassembled.
5. **CI.** There is none. The badges in the README are static and the check
   scripts have known breakages listed under Known gaps.

## What this data does not support

Stated so nobody builds on a false premise.

- **It is not an ARC evaluation set.** All 400 tasks are from the ARC-AGI-1
  *training* split. Reporting an ARC score against it measures nothing.
- **The routes are not canonical.** They are one maker's way of solving the
  task. There is no claim that they are minimal, natural, or what a human would
  do.
- **There are no negative or failed trajectories.** Every published episode
  reaches its target. Any method that needs failures has to generate them.
- **Inputs are RE-ARC samples, not original ARC pairs.** The originals are
  reproduced and checked (`pipeline/probe_originals.py`), but they are not what
  the episodes are drawn from.
- **`handcraft` is small and beta.** Nine tasks, half-variants only. It is there
  to show that several routes to one target are recordable, not to support a
  study on its own.

## Open questions we did not resolve

- Does route length correlate with anything a learner cares about, or is it
  noise? (Our position is that it is close to noise, but we have not shown it.)
- Is the operation imbalance a problem to fix in the data, or a property of the
  task distribution that a method should handle?
- Do the routes carry pipeline-specific regularities that a model can exploit
  without learning the task?
- Does showing a demonstration's route, rather than only its pair, change
  few-shot performance?

Contributions on any of these, including negative results, are welcome. Open an
issue on [QAZyunho/SOLAR-V2](https://github.com/QAZyunho/SOLAR-V2/issues).
