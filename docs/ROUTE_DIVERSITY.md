# 한 과제에 여러 경로 — 실험 기록

2026-09-30 ~ 10-02. 물음은 하나다. **같은 ARC 과제를 푸는 유효한 ARCLE 궤적이
여럿 나올 수 있는가, 그리고 무엇이 그걸 갈라놓는가.**

좋은 경로를 찾는 실험이 아니다. 배포 게이트는 따로 있고, 여기서 세는 것은
가짓수다. 다만 "유효"의 기준은 느슨하지 않다 — 뽑은 인스턴스를 전부 풀고,
정답을 흐트러뜨려도 같은 경로를 내놓아야 한다(`dep == 0`).

자료 전부: `/hdd_data/yunho/route-diversity/`
(`prompts/` 지시문, `results/` 측정값 JSON, `logs/` 실행 로그, `scripts/` 측정 코드)

---

## 1. 무엇을 "다른 경로"로 세는가

경로의 신원은 **(op 이름, 실제로 고른 칸의 집합)의 나열**이다. 인스턴스 5개에
대한 나열을 묶어 하나의 서명으로 쓴다.

선택을 bbox로 적었는지 칸 목록으로 적었는지는 보지 않는다. 같은 칸을 고르면
같은 선택이다. 이게 중요한 이유는 한 번 틀렸기 때문이다 — 표기를 그대로 비교해
"82%가 다른 일"이라고 셌다가, 마스크로 다시 재니 76%였다.

두 경로의 관계는 셋으로 가른다.

| | |
|---|---|
| 같음 | 단계별로 op과 고른 칸이 모두 같다 |
| 순서만 | 같은 단계들의 순서만 다르다 |
| 다른 일 | 그 밖 — 다른 op을 쓰거나 같은 op을 다른 영역에 쓴다 |

측정 코드는 `scripts/diversity_all.py`.

## 2. 출발점 (10-01)

그동안 만들어둔 maker 변형 전부(`maker/` 아래 모든 폴더)를 같은 인스턴스에
돌려 셌다.

```
과제 400,  과제당 푸는 코드 5.7개  ->  서로 다른 경로 2.7가지
경로 2가지 이상  316 / 400
경로 1가지뿐      84 / 400
기준 외 경로 692개 중  순서만 68 (10%)  다른 일 624 (90%)
```

**코드가 많다고 경로가 늘지 않는다.** 5.7개에서 2.7가지면 절반 이상이 같은
궤적이다. `arc-best`·`arc-agi1-noref` 계열은 서로 복사본이거나 같은 곳으로
수렴한다.

계열별로 "그 계열만 낸 경로"를 과제 수로 나누면 순위가 뒤집힌다.

| 계열 | 과제 | 그 계열만 낸 경로 | 과제당 |
|---|---|---|---|
| alt (대안 생성) | 23 | 33 | 1.43 |
| golf (짧게) | 25 | 33 | 1.32 |
| redo-* (지시 바꿔 재생성) | 124 | 122 | 0.98 |
| var (교란 재생성) | 128 | 116 | 0.91 |
| base (arc-best/noref) | 396 | 339 | 0.86 |
| noO (O 안 보여주고) | 33 | 5 | **0.15** |
| arc-agi-1 (배포본) | 394 | 0 | 0.00 |

`base`가 총량 1위인 것은 396개에 돌렸기 때문이다. `noO`는 다양성 목적으로
쓸 이유가 없다.

## 3. 네 가지 지시 (10-01 ~ 10-02)

지시문 전문은 `prompts/INSTRUCTIONS.md`. 네 갈래 모두 가드 두 문장을 공유한다.

> Every selection must be something you can name from the input before you know
> the answer — a rectangle, a connected object, all cells of one colour, a row,
> a column, the cells a copy lands on.
>
> And the operations must be derivable from the input grid and the worked
> examples alone: handed a different answer grid, this function must return the
> same operations.

가드가 없으면 답을 읽는다. 가드를 뺀 `golf2`는 25개 중 2개가 `dep 1.00`
(정답을 흐트러뜨리면 경로가 통째로 바뀜)이었고, 가드를 넣은 갈래는
**137개 maker 중 0개**였다.

### 3.1 짧게 (`golf84`, 84개)

이미 푸는 maker를 보여주고 "같은 일을 더 큰 획으로, 더 적은 동작으로".

```
생성 84/84,  인스턴스를 다 푸는 것 78,  새 경로 36  (46%)
경로 1가지 -> 2가지 이상  40 / 84
```

25개 표본에서는 23/25(92%)였는데 84개에서 46%로 떨어졌다. 표본 25개는 이미
경로가 여럿이던 과제였고, 84개는 **어떤 지시로도 안 갈라진 과제**다.

### 3.2 재표집 (`resample1`, 400개)

참조도 피드백도 없이 같은 프롬프트를 다시 뽑는다. 준비 비용 0.

```
과제 400,  그 갈래만 낸 경로 129,  과제당 0.38
```

### 3.3 남의 풀이 참조 (`barc1`, 160개)

[BARC](https://github.com/xu3kev/BARC) seed를 참조로 붙였다. seed 160개가
우리 400개와 **전부** 겹친다. `generate_input()`은 떼어냈다 — 인스턴스는
RE-ARC generator에서 나오고, seed의 생성기를 보여주면 베낄 이유가 생긴다.

> That is one person's reading of this task, written in their own vocabulary
> rather than ARCLE's. Where it carves the problem differently from the maker
> above — different objects, a different order, a different thing held fixed —
> follow the reading in the reference, not the one already here.

```
과제 160,  그 갈래만 낸 경로 67,  과제당 0.47  (네 갈래 중 최고)
```

과제당 수율은 가장 높지만 seed가 있는 160개에만 쓸 수 있다.

### 3.4 다르게 묶기 (`group1`/`group2`/`group3`)

앞 세 갈래가 전부 실패한 41개를 보고 세운 가설: 막혀 있는 것은 어휘도 길이도
아니고 **무엇을 한 단위로 보는가**다.

> What must change is the unit of work. Look at what this route treats as one
> thing — one object, one cell, one row, the whole grid — and write the same
> rule against a different unit. (...) A longer route is fine. What is not fine
> is the same decomposition written again — if you cannot see a second way to
> carve this task, say so plainly instead of renaming variables.

| | 대상 | 다 푼 것 | 새 경로 | |
|---|---|---|---|---|
| `group1` | 41 (경로 1가지) | 38 | **35** | 92% |
| `group2` | 105 (경로 2가지) | 98 | **85** | 87% |
| `group3` | 254 (경로 3가지 이상) | 진행 중 | | |

**네 갈래 중 가장 생산적이다.** 다른 셋이 전부 실패한 과제에서 92%,
이미 경로가 둘인 과제에서도 87%로 포화 기미가 없다.

마지막 문장("두 번째로 자를 방법이 안 보이면 그렇다고 말하라")이 실제로
작동했다. `d10ecb37`의 생성 코드에 이렇게 적혀 있다.

```
# I found no second non-redundant way to split this task. Every crop is anchored at ...
```

규칙이 "입력의 좌상단 2×2를 남긴다"이고 2×2가 과제 고정 상수라 자를 단위가
하나뿐이다. **진짜 외길로 확인된 유일한 과제다.**

## 5. 품질 — 새 갈래가 쓸 수 있는 것인가

84개 과제에 대해 배포 게이트 전수 채점 (`results/newarms.json`).

| arm | maker | 배포 기준 전부 통과 | `dep > 0` |
|---|---|---|---|
| `arc-agi-1` (배포본) | 84 | 84 | 0 |
| `golf84` | 84 | 83 | **0** |
| `resample1` | 84 | 83 | **0** |
| `barc1` | 29 | 27 | **0** |

**답을 읽는 maker가 하나도 없다.** 떨어진 것은 `solve` 각 1개와 `zero` 각
1개뿐이다.

임의 마스크(선택이 자기 bbox의 진부분집합인 비율)는 따로 쟀다.

| arm | 평균 임의 마스크 | 마스크가 0.25 넘게 나빠진 과제 | 어휘가 바뀐 과제 |
|---|---|---|---|
| `arc-agi-1` | 10% | — | — |
| `golf84` | 22% | 20 | 14 |
| `resample1` | 16% | 8 | 16 |
| `barc1` | 15% | 2 | 6 (29개 중) |

**이 축은 기각 사유가 아니다.** 임의 마스크가 뜻하는 것은 "궤적 밖에서 한
계산"이지 "답을 읽었다"가 아니다(그건 `dep`가 본다). 다양성 재료로는 무관하고,
이 중 하나를 배포본으로 승격할 때만 다시 보는 값이다 — 승격 게이트에는 이미
들어 있다.

다만 경향은 분명하다. **짧게 만들라는 지시는 마스크로 값을 치른다.**
`golf84`는 어휘 14개를 바꾸면서 마스크를 20개 과제에서 악화시켰고,
`resample1`은 어휘 16개를 바꾸면서 8개만 악화시켰다.

## 7. 밟은 것

측정 쪽에서 네 번 틀렸고, 네 번 다 실제 데이터에 대보고서야 알았다. 기록해
두는 이유는 같은 모양의 실수를 또 하기 때문이다.

| 틀린 측정 | 무엇을 재고 있었나 | 어떻게 드러났나 |
|---|---|---|
| 출력 격자를 입력 크기로 잘랐다 | 패딩값 10을 색으로 셈 | 결함 1개가 106개로 부풀었다 |
| 배경 = 최빈색 | 3×3에서 모양색이 0보다 많으면 뒤집힘 | 111개 중 대부분이 거짓 |
| hold 기록 전체 = 역할 | 31aa019c는 per-cell 색 수백 개 | 54개 중 10개만 진짜 |
| 유지된 색 중 1등 = 그 색의 역할 | 빈도는 인스턴스마다 변함 | 671개 전부 오검출 |

공통점은 **쉽게 셀 수 있는 대용물을 재고 그걸 묻고 싶었던 것이라 불렀다**는
점이다. 숫자가 크게 나오면 대용물을 의심하는 편이 맞았다.

운영 쪽에서도 둘 밟았다.

- 큐가 `/usage`의 **주간만 보고 세션은 안 봤다.** 세션이 차자 호출이 즉시
  실패했고, 루프가 그걸 "실패한 라운드"로 세서 재시도 6번을 2분 만에 태우고
  죽었다. 이제 세션도 보고, 5분 안에 끝났는데 maker가 안 늘면 한도에 막힌
  것으로 보고 재시도로 세지 않는다.
- 변환 함수가 **원래 순서를 후보 목록 맨 뒤에 두어** 이미 멀쩡한 에피소드도
  재배치했다. 결함 26개를 고치면서 나머지 5972개를 조용히 다시 쓸 뻔했다.

## 8. 남은 것

- **6개 과제가 아직 경로 1가지.** 그중 `d10ecb37`은 모델이 외길이라고 명시했고,
  `5daaa586`·`ce602527`은 **코드는 다시 썼는데 궤적이 같다**(유사도 0.53, 0.70).
  ARCLE op 어휘가 좁아 "다르게 생각한 것"이 "다르게 실행한 것"으로 항상
  이어지지는 않는다. 나머지 3개는 새 분해를 시도했다가 인스턴스를 못 맞춘
  정확도 실패다.
- **인스턴스 5개 기준.** 15개로 올리면 "다 푸는 코드"가 줄어 경로 가짓수도
  줄 수 있다. 지금 수치는 상한에 가깝다. LLM은 안 든다.
- **"다른 일"의 폭을 안 쟀다.** 물체를 다르게 묶은 것과 완전히 다른 개념으로
  푼 것이 한 칸에 들어가 있다.
- 분할·병합을 전수로 적용하면 141개 과제에 경로를 하나씩 더 붙일 수 있다.
  아직 maker로 만들어 넣지는 않았다.

## 9. 사람의 풀이 여섯 가지 (10-06 ~ 10-10)

### 9.1 무엇을 물었나

3절의 네 지시는 모두 **모델에게 다르게 생각하라고 말하는** 방식이었다.
여기서 묻는 것은 다르다. **같은 과제를 사람 여섯이 각자 푼 것이 있을 때,
ARCLE 궤적도 여섯 가지로 갈라지는가.**

재료는 Google Code Golf 2025 제출물이다. 바이트 수를 줄이려고 쓴 코드라
읽히려고 쓴 코드가 아니지만, **짧게 만들려면 과제를 어떻게 보느냐가 먼저
정해져야 한다.** 그 밑에 깔린 읽기가 재료다.

### 9.2 출처

처음에는 집계 저장소를 봤는데 과제당 채택본이 **하나뿐**이라 다양성 재료가
못 된다. 팀 저장소를 각각 받아야 같은 과제에 대해 서로 다른 사람이 쓴 풀이가
여러 개 생긴다.

| arm | 저장소 | 유효 과제 |
|---|---|---|
| `cg_cgi` | `Seek64/NeurIPS-Code-Golf-2025` | 400 |
| `cg_aggregate` | `arc-code-golf/solutions` | 399 |
| `cg_oxjam` | `xsot/google-code-golf-2025` | 398 |
| `cg_camjam` | `intgrah/golf` | 396 |
| `cg_itertools` | `Natanaelel/GoogleCodeGolf2025` | 369 |
| `cg_lv1dev` | `lv1-dev/google-code-golf-2025` | 368 |

**"유효"는 추측이 아니다.** ARC 원본의 train+test 쌍 전부에 돌려서 재현되는
것만 셌다(`collect_golf.py`). 과제 번호와 task id의 대응은 원본 쌍의 해시로
맞췄다.

### 9.3 어떻게 넣었나

**한 arm에는 한 팀의 풀이만 넣는다.** 여섯을 한꺼번에 보여주면 모델이 그중
하나로 수렴할 수 있고, 그러면 무엇이 무엇을 낳았는지 가릴 수 없다.

지시문 전문은 `/hdd_data/yunho/route-diversity/prompts/`에 과제별로 있다.
핵심은 두 문장이다.

> 짧게 쓰인 것은 거기서 바이트가 목적이었기 때문이다. 여기서는 아니다.
> **다른 읽기를 따른 긴 경로가 원하는 답이다.**

3절의 `golf84`가 "짧게 만들라"였던 것과 정반대다. 짧게 만들라는 지시는
5절에서 **마스크로 값을 치렀다**(20개 과제 악화). 여기서는 참조만 짧고
요구는 "다르게"다.

selection·derivability 두 제약은 모든 갈래와 동일하게 붙었다.

### 9.4 결과

6개 arm, 2330개 maker를 생성했다. 인스턴스 5개 기준 전수 400과제 집계
(`eval_cg6.py`, 400/400, 실패 0):

```
누적 참조        새 경로   과제당   증가분
1개 cgi            171     0.43
2개 +oxjam         295     0.74     +124
3개 +camjam        428     1.07     +133
4개 +aggregate     516     1.29      +88
5개 +itertools     611     1.53      +95
6개 +lv1dev        697     1.74      +86
```

**참조를 늘리면 계속 번다.** 증가분이 133 → 88 → 95 → 86으로 완만히 꺾이지만
여섯 번째도 86개를 새로 벌었다. 포화가 아니라 체감이다.

10개 과제 파일럿에서 과제당 1.70을 봤고 전수에서 1.74가 나왔다. 표본 10개의
수치가 400개에서 그대로 맞은 드문 경우다.

전체 재집계:

```

경로 총합           1820     2517
과제당               4.55     6.29
경로 2가지 이상    397/400   397/400
경로 1가지뿐           3         3
```

**참조 여섯은 덮는 과제를 늘리지 못했다.** 2가지 이상인 과제는 397개로
그대로고, 경로가 하나뿐인 3개는 여섯 참조로도 안 갈라졌다. 번 것은 전부
**이미 여러 갈래가 있던 과제의 깊이**다. 8절이 적은 대로 그 3개는 ARCLE op
어휘가 좁아서 갈리지 않는 쪽이지, 재료가 모자라서가 아니다.

과제당 총 경로 분포는 4개(61) · 6개(64) · 3개(46)에 몰리고 꼬리가 19개까지
간다. 과제당 새 경로 분포는 `{0:103, 1:109, 2:69, 3:58, 4:35, 5:20, 6:6}` —
**297개 과제가 최소 하나는 얻었고**, 6개 과제는 참조 여섯이 전부 갈렸다.

arm별 단독 해결률은 cgi 354 · oxjam 351 · aggregate 347 · camjam 343 ·
lv1dev 305 · itertools 302. 여섯이 모두 푼 과제가 218개(55%), 하나도 못 푼
과제는 7개다.

수율(그 갈래의 단독 경로 ÷ 덮은 과제)로 보면 code-golf 참조는 0.75 선으로,
"다르게 묶기"(0.78~0.92)에 이어 두 번째다. BARC 참조(0.43)보다 높다.
**사람이 실제로 다르게 푼 기록이 모델에게 다르게 생각하라고 말하는 것보다
낫다**는 3.3절의 관찰이 더 강한 재료에서 재현됐다.

### 9.5 밟은 것

- **처음에 code-golf 코드를 참조로 넣지 않았다.** 지시문만 code-golf식으로
  쓰고 실제 제출 코드는 넣지 않은 채 "code golf 갈래"라고 불렀다. 사용자가
  "arc code golf 코드를 찾아서 쓰자는 말이었어"로 바로잡았다. 7절의 측정
  실수와 같은 모양이다 — **하려던 것의 대용물을 해놓고 그것이라고 불렀다.**
- **수율 평가가 메모리를 먹었다.** `maker/cg_oxjam/150deff5`가 남은 칸의
  frozenset을 키로 타일링 탐색을 메모이즈해서, 23×27 인스턴스 하나에서
  24GB를 넘겼다. OOM이 뜬 게 아니라 기계가 느려져 접속이 안 됐다.
  - `RLIMIT_AS`만으로는 부족했다. `MemoryError`는 잡히는데 주소공간이
    상한에 고정된 채라 다음 `io.open`이 실패한다.
  - **과제마다 fork**(`isolate.py`, 3GiB·600초)로 해결했다. 폭주하는 maker가
    있어도 그 과제만 잃고 부모는 10MB에 머문다. 400/400 완주, 실패 0.
  - cgroup은 `MemoryMax`만 쓴다. `MemoryHigh`를 같이 걸었더니 죽이는 대신
    무한정 멈춰세웠다 — 그게 바로 사고 때의 모습이라 쓰면 안 된다.
  - 60개 동시 `claude -p`에서 병렬 3으로 낮춰, 최대 점유가 ~24GB에서
    ~0.8GB가 됐다.

## 10. 기계적 변환을 maker로 (10-11)

4절에서 분할·병합이 유효한 경로를 낸다는 것까지 봤고, 2절의 집계에는 넣지
않았다. 변환을 메모리 안에서 적용해 봤을 뿐 maker 파일로 굳히지 않았기
때문이다. 이번에 굳혔다. **LLM은 한 번도 부르지 않았다.**

### 10.1 만드는 방법

원본 maker 파일을 그대로 베끼고 `derive_operations`의 이름만
`_base_derive_operations`로 바꾼 뒤, 변환을 씌운 새 `derive_operations`를
뒤에 붙인다. `GridMaker`가 부르는 이름은 호출 시점에 풀리므로 자동으로
변환본을 쓴다. 인자 수는 원본과 맞춘다 -- `call_derive`가 개수로 분기한다.

변환은 `(ops, sels)`만 읽는다. 입력 격자도 답 격자도 보지 않으므로,
**원본이 유도 가능하면 변환본도 유도 가능하다.** 이 갈래에 한해 유도 가능성은
증명되는 성질이지 검사하는 성질이 아니다.

- **분할** -- 한 번에 칠하던 떨어진 덩어리들을 덩어리별로 나눠 칠한다.
- **병합** -- 같은 색을 연달아 두 번 칠하면 한 번에 칠한다.

**arm을 둘로 나눴다.** 둘 다 새 경로를 내는 과제가 16개 있는데, 한 arm에
합치면 과제당 하나만 남아 그 16개를 잃는다. 141개가 아니라 157개가 된 이유다.

### 10.2 결과

```
mech_merge  117 과제
mech_split   40 과제
합계        157

인스턴스 5개 재생 통과   157 / 157
그중 정말 새 경로        155        (2개는 기존 경로와 일치)
```

실패 0. 메모리 안에서 쟀던 것이 파일로 굳힌 뒤에도 그대로 재현됐다 --
인자 수·이름 해석·셀 좌표 형식 세 군데가 틀어질 수 있어 따로 확인했다.

### 10.3 왜 이것을 먼저 했나

수율로는 155/157 = 0.99로 지금까지 중 가장 높지만, 그건 **새 경로를 내는
과제만 골라 만들었기 때문**이라 다른 갈래의 수율과 나란히 놓을 수 없다.
의미 있는 비교는 비용 쪽이다. LLM 호출이 0이고 사람 참조도 필요 없다.

다만 이것이 **얕은 다양성**이라는 점은 분명하다. 한 자리만 바꾼 경로이고,
같은 분해를 다른 입자로 적은 것이다. 3절의 "다르게 묶기"가 과제를 다시 읽는
것이라면 이쪽은 같은 읽기를 다시 적는 것이다. 수를 보탤 때 그 차이를 함께
적어야 한다.

### 10.4 참조를 세 종 더 찾았다

9절의 여섯 팀 외에 세 종을 더 확인했다. ARC 원본 train+test 쌍 전부에
돌려서 재현되는 것만, 그리고 기존 여섯과 바이트 동일한 것은 `dup`으로 뺐다.

| arm | 저장소 | 유효 |
|---|---|---|
| `cg_cristianoc` | `cristianoc/arc-code-golf-solutions` | 400 |
| `cg_sakana` | `SakanaAI/google-code-golf-2025` | 380 (dup 20) |
| `cg_cctofu` | `cctofu/golf-championship` | 46 (bad 354) |

`cristianoc`는 **이미 디스크에 받아놓고 여섯 arm에 넣지 않았다.** 9절을
쓸 때 집계 저장소 하나와 팀 저장소 다섯만 세고, 먼저 받아둔 것을 빠뜨렸다.

### 10.5 메운 구멍

프롬프트를 써놓고 생성하지 않은 두 갈래를 끝냈다.

```
group3   219 -> 254   (35개)
golf292  183 -> 292   (109개)
```

`barc1`이 160개에서 멈춘 것은 **재료가 없어서다** -- BARC seed는 저장소
전체에 166개뿐이고 우리 400과제와 겹치는 것이 정확히 160개다. `alt`·`var`·
`noO`가 400에 못 미치는 것도 중간에 끊긴 게 아니라 애초에 선별된 부분집합을
대상으로 한 갈래여서다.

## 11. 프롬프트는 하나다 (10-12)

갈래마다 프롬프트 전문이 많이 달라 보이는데, **바뀌는 것은 한 블록뿐**이다.
배포된 400개를 쓸 때부터 지금까지 같은 프롬프트다.

```
SYSTEM (약 26,000자)                       고정, 모든 갈래 공통
USER
  1. Task ID                               고정
  2. 목표 문구 (NO WASTED ACTIONS)          고정
  3. feedback_block      ◀ 갈래가 바뀌는 유일한 자리
  4. RE-ARC verifier 전문    --include_verifier (기본 ON)
  5. RE-ARC 생성기 전문                      고정
  6. I/O 예시                               고정
  7. object hint         --include_object_hints (기본 OFF)
  8. arc-dsl solver          --include_solver (기본 OFF)
  9. "세 함수를 써라"                        고정
```

실행 명령도 `--output_subdir`와 `--task_feedback_file` 두 인자만 다르다.
전문과 슬롯 템플릿은 `route-diversity/templates/PROMPT_ARCHITECTURE.md`.

### 11.1 3번이 비어 있는 갈래가 둘 있다

`--task_feedback_file`을 안 주면 블록이 통째로 사라진다.

- **기준 `arc-agi-1`** — 맨땅. 앞선 풀이도 외부 참조도 없이 나온 읽기
- **재표집 `resample1`** — 같은 프롬프트를 다시 뽑은 것. 가장 깨끗한 대조군

나머지 갈래는 전부 **기준 maker의 `derive_operations` 전문을 3번에 넣고**
거기서 갈라지게 한다. 그래서 기준은 특별한 자리에 있다.

정확히는 배포 세트 400개 중 **49개가 승격으로 교체됐다**(`round4` 16,
`zero3` 8, `depfix` 6, `zerofix`/`zerofix2` 6, 그 외 3). 다양성이 아니라
품질 축(헛도는 동작·0색·유도 가능성) 때문이고, 그 버전들도 같은 프롬프트의
다른 3번 내용에서 나왔다.

### 11.2 "고치기"가 아니라 "보고 다시 쓰기"

3번에 기존 코드를 넣지만 출력은 패치가 아니다. SYSTEM이 세 함수를 전부
요구하므로 파일 전체가 새로 온다. 실제로 얼마나 베끼는지 재봤다
(`cg_cgi` 대 기준, 120개 과제).

| 함수 | 글자까지 동일 | 평균 유사도 |
|---|---|---|
| `sample_colors` | 13 / 120 | 0.60 |
| `generate` | **0 / 120** | 0.30 |
| `derive_operations` | **0 / 120** | 0.41 |

**코드 재사용은 사실상 없다.** 그런데도 궤적이 같아지는 과제가 있다 --
참조 6종이 모두 푼 218개 중 45개가 새 경로 0이었다. 코드를 다시 쓰면서도
같은 읽기로 돌아온다는 뜻이다.

3번의 공통 꼬리에 이런 문장이 있다.

> Where the two agree there is nothing to change and **you should say so**.

**같은 경로로 돌아가도 된다고 허락하는 문장**이다. 수렴의 일부는 여기서
나올 수 있다. 아직 빼고 재보지 않았다.

### 11.3 참조는 첫 번째가 아니다

4번(verifier)과 5번(생성기)은 둘 다 Hodel이 쓴 것이고 **둘 다 규칙을 담고
있다.** 같은 과제에서 생김새는 전혀 다르다.

- **생성기** -- 입력과 출력을 같은 자리에 따로 그린다. 좌표를 정하고 거기에
  칠한다. 규칙이 구성 과정에 들어 있다
- **verifier** -- 입력만 받아 출력을 계산한다. 물체를 찾아 bbox에서 선을
  유도한다

`--include_verifier`의 기본값이 ON이고 어떤 실행도 끄지 않았으므로,
**모든 maker가 이미 Hodel의 읽기 두 가지를 보고 썼다.** code-golf 코드를
주는 것은 첫 참조가 아니라 **세 번째 참조**다.

같은 저자의 읽기 둘을 이미 본 상태에서도 제3자의 읽기를 더하면 과제당
1.00 → 3.94가 된다는 뜻이라, 결과는 오히려 강해진다. 다만 수렴의 일부는
**이미 본 Hodel의 두 읽기로 돌아간 것**일 수 있다. 확인하려고 verifier를
뺀 대조군(같은 참조 `cgi`, 50개 과제)을 돌리는 중이다.
